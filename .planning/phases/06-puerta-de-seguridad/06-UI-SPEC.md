# Phase 6 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope.** Phase 6 adds no new screen, component or token. Its UI surface is (a) 06-03: which buttons open the existing sensitive-action dialog and which send directly, from the "Acciones del host" card, the Ctrl K search and the container/file action buttons; and (b) 06-06: how views behave when the hub answers `502 agent_response_too_large`, keeping the last valid data. 06-01, 06-02, 06-04 and 06-05 are server-side and have no UI contract beyond showing the server's Spanish `error` text in the existing dialog notice.

**Authority.** `DESIGN.md` (repo root) overrides this file where they differ. `CODING_STANDARD.md` applies: tests assert state, outcome or structure, never copy. `AGENTS.md` applies: this repo runs Next 16.4.6 with breaking changes. This phase touches only client components (`"use client"`) and CSS Modules, so it needs no new Next API; any server-route edit made by these plans must be preceded by reading `node_modules/next/dist/docs/`.

**Rule that governs everything below (D-07).** The server is the authority; the UI only explains. The UI opens the passkey dialog exactly when `requiresVerificationForAction` / `requiresVerificationForCommand` (from `src/lib/sensitive-actions.ts`) return true, and never keeps a second list of protected ids.

## Interaction Contract

### I-1. One dialog, no native dialogs
- Every protected action and command opens `useSensitiveAction().dialog` (`dialog[data-sensitive-action]`). No `window.confirm` anywhere in these flows (`clean-images` loses its `window.confirm`; a Playwright `page.on("dialog")` listener fails the test if a native one appears).
- Nothing is sent until the Operator presses the confirm button (`[data-confirm]`). Escape or Cancelar closes without any request. Escape and the close button are inert while `data-phase` is `verifying` or `executing` (existing).
- Non-protected actions keep the existing simple dialog in `dashboard.tsx` (no `data-sensitive-action`): `start`, `trash`, `move`, `restore`. This is the only visible difference between the two dialogs, and it is intentional (D-01, D-02).

### I-2. Who opens what (derived from the manifest, never hard-coded in `src/components`)

| Entry point | Protected (opens the sensitive dialog) | Exempt (no sensitive dialog) |
|-------------|----------------------------------------|------------------------------|
| Card "Acciones del host" (`[data-host-command]`) | `deploy-now`, `reconnect-apps`, `backup-now`, `clean-images` | `check-health`: sends directly |
| Ctrl K search options and the `D` `W` `B` shortcuts | all host commands except `check-health` | `check-health` and the `H` shortcut: close the palette and send directly |
| Container rows | `stop`, `restart`, `update-container` (and the existing remove and reboot flows) | `start` keeps the simple dialog |
| Files and trash | `purge`, `empty-trash` | `trash`, `move`, `restore` keep the simple dialog |

The `pause-follower`, `resume-follower` and `run-security` commands are reachable only from the search list (not the card); they follow the same rule.

### I-3. Direct send of `check-health`
- Card: the button disables while a send is in flight or pending; `[data-command-state]` shows `executing` (`En curso`), then the result, exactly as before. The new `sendHostCommand` carries a fresh `Idempotency-Key` per click.
- Search: choosing it (or pressing `H`) closes the palette, returns focus to the opener, sends, emits `maintenance-refresh`, and reports through `onNotice` (success, rejection or unconfirmed, see Copywriting). A second `H` while one is in flight is ignored.
- Both entry points are disabled when `canMutate` is false (host disconnected or busy), as today.

### I-4. Confirmation outcome mapping (existing, must be preserved on the card)
`onSettled` results apply to the card's `held` state through the same function as a direct response:
- succeeded: result detail, `maintenance-refresh` emitted.
- pending (network failure, or 5xx other than 503): `Pendiente de verificar`, card buttons disabled, never retried automatically, dialog shows the `peach` notice and offers `Cerrar`.
- failed (4xx, or 503 which means nothing was sent): dialog shows the `loss` notice, `Cerrar`; card shows the server `error` or `Operación rechazada`.
- 403 `recent_verification_required` while confirming: the dialog flips to the verification hint and asks again with the same idempotency key; no automatic resend.

### I-5. Focus and keyboard
- On open, focus goes to `[data-initial-focus]`: the typed-confirmation field if present, the password field if needed, otherwise Cancelar (least destructive choice). Closing returns focus to the element that opened it.
- Only one modal at a time: the Ctrl K shortcut is ignored while another `dialog[open]` exists (existing).

### I-6. Too-large responses keep the last valid data (D-11)
- Never render partial lists, partial logs or truncated JSON. The server answers 502 with a stable `code`; the view shows the message and keeps the previous data of the same host and scope.
- `useHostRead`: on `!response.ok`, read `code` and `error` from the body; for `agent_response_too_large` the error is the server message, otherwise the existing generic message. Last data (`old.data`) is retained for the same host key. Views that already render `error` need no new markup.
- File list: a failed refresh of the same root and folder keeps the entries and shows the state line (`role="alert"`, `data-files-error`); changing root or folder discards the previous entries, because showing another folder's rows would be misleading. While a refresh is running and no error exists the line reads `Leyendo el NAS…` (existing). Error wins over busy.
- Maintenance status: `SnapshotState.tooLarge` selects the note `data-snapshot-note="too-large"`; the snapshot is kept and marked stale; the next good response clears it. Without any snapshot the phase is `error` with `tooLarge` true. Other views that read the snapshot keep their usual stale indication.
- Container logs viewer (`container-logs.tsx`): unchanged by the plans, and the existing code already satisfies D-11. A failed live-follow poll only sets `error` and leaves `lines` untouched, so the last lines stay visible under the server `error` in its `role="alert"` line. A failed first read, size change or refresh has no previous lines by design, because `restart()` empties the buffer before reading; there the viewer shows only the `error`.

### I-7. Mobile and accessibility
- Dialog width, 44px targets and the stacked footer (`flex-wrap`) already hold at 360px; no media query is added. The note, state line and toast wrap (`overflow-wrap: anywhere` in the dialog).
- Roles: dialog is a native modal `<dialog>` with `aria-labelledby`, optional `aria-describedby` (the host line), `aria-busy` while in flight. Pending notice `role="status"`, error notice `role="alert"`, maintenance note `role="status"`, file-list error `role="alert"`, toast `role="status"`.
- Reduced motion: the dialog's translate transition is already wrapped in `prefers-reduced-motion: no-preference`; add no animation.

### I-8. Focal points and icon-only controls
- Focal point, sensitive dialog: the title (21px Unbounded, the largest text on screen) names the action, and the confirm button (`[data-confirm]`, the only filled control, accent or `--loss` tone) is the single call to action. Nothing else in the dialog is filled or larger.
- Focal point, "Acciones del host" card: the action rows (`[data-host-command]`, 46px, one per command) are the focal content; the card adds no heading emphasis, badge or accent beyond the rows' existing state markers.
- Every icon-only control (44x44px) carries a Spanish `aria-label` naming its action, never the icon: the dialog close button keeps `Cerrar`. Any icon-only button this phase adds uses the same pattern. Icons that sit beside visible text (shield, triangle, fingerprint) are `aria-hidden`.

## Open items for the planner (not blocking the contract)

1. **Duplicate hook.** 06-03 adds `data-command-option` to each search option, but `command-search.tsx` already renders `data-search-command={c}` on exactly those buttons and no test or code reads either. Recommended: reuse `data-search-command` and skip the new attribute. If the plan keeps the new name, keep both and do not rename the old one.
2. **Host line in the dialog.** 06-03 only asks for `description` with the host name in `dashboard.tsx` `request()`. This contract asks for the same one-line description in `maintenance-extras.tsx` and `command-search.tsx` (one property each, value `scope.host?.name`), so the three entry points look the same.
3. **Toast has no error tone.** The shared `.toast` always shows a green check (`CircleCheck`, `--gain`), even for the failure messages already sent through `setToast`. The `check-health` failure text in this contract states the problem in words so colour is not the only signal. Adding a tone variant is out of scope for Phase 6.
4. **Generic consequence for most host commands.** The copy `La acción se ejecutará una sola vez en el host seleccionado.` is the 06-03 default. A per-command sentence (for example for `deploy-now` and `backup-now`) would be clearer but would add a command-keyed copy table; not required here.
5. **Logs viewer on a 502.** Resolved from `container-logs.tsx` (see I-6); no action.
